# HeapHopper
## General Rundown
1. Use "heap states" to indicate that the i'th operation caused used the heap in some way. Given these recordsings up states, combine them together to make a final observation
    1. There are two types of operations that interact with heap:
        1. Direct: using heap as expected via mal/fre
        2. Indirect: modifying existing heap mem via flaws like buf ovfs
    2. Therefore, a transaction is an operation that modifies a heaps state indirect/directly
    3. The Transactions we care about, as they are the primitives that make up a UAF exploit are:
        1. Malloc
        2. Free
        3. Overflow: To verify that an ovf happned, we need to look out for two common causes:
            1. Missing Bounds Check -> Write larger than allocation target
            2. Smaller than intended allocation returned/calculated
        4. Use After Free: access to memory after it's been freed
        5. Double Free: pointer to free'd mem is used as arg for `free`.
        6. Fake Free: attacker passes pointer to free such that a chunk of non heap memory is treated as a freed chunk, and reused on future mallocs. we can track this via calls to free with starting addresses never used/reused.
    4. This tells me that its possible worth picking specific UAF-based exploits rather than just different kinds of UAFs on different date types, etc.
    5. Since alot of these transitsions use arguments i.e. how many byttes were overflowed? how many bytes freed, etc, HH handles that via symbolic execution.

Given the heap state + transitions/transformations, HH asks whether some sequence of actions can drive the allocator into a state that gives an attacker useful exploit primitives.

## Evaluation
They evaluated HH via three ways:
1. Given an allocator implementation, and using the same bounded model configuration, what primitives can be reached?
2. Given we know of an attack, if we translate the attack sequence into HH's transition vocabulary, can it recreate it?
3. How does HH do with specific case studies?
    1. Can the 1 byte null overflow mitigation be bypassed?
    2. Does their replacement patch block the modled technique?
    3. Does adding tcache make ptmalloc easier to exploit?

HH considers a successful result to be one that contains one or more of the following exploit primitives. It's not interested in full AEG:
1. Overlapping Allocation: malloc returns mem overlapping an allocation that is still live
2. Non-heap allocation: malloc returns mem outside heap i.e. stack mem
3. Arbitrary Write with Constraints: attacker controls destination/write, but the target mem must satisfy some constraints
4. Arbitrary Write: unconstrained control of write

Therefore, for my thesis, we should probably note which of these primitives were generated by manually tracing first, then during the test, see if the primitives classified align with ours.

For experimental configuration they use a bounded model with the following configurations:
1. Types of Transactions: what transactions are allowed to be used in the test run
2. Depth: How many transactions we are allowed to run on a single test run (since recall, test runs use the allowed transactions, and do different permutation orders)
3. Alloc Sizes: diff alloc sizes can go into different bins, so need to account for that
4. Overflow lengths: since we can overflow by x bytes, they only do a 1 byte ovf and 8 byte, since the most common overflows are either to simply corrupt a value i.e. null byte overflow in heap metadata, or address overwrites, which are 8 bytes
5. UAF Size: IF the test uses UAF, how large is the arbitrary write

The idea behind these specific configuration fields is because they cannot explore every possible execution, so they focus on these core "elements" of a corrupted execution.

Now given this, they ran their executions, and created their results table:
1. Rows represent the allocator version used for the tests
2. Columns are the four aformentioned primitives
3. Essentially, they record that for the i'th allocator, if we want to reach a state with the j'th primitive, we need to use the transactions within the set `{set}: ...`, and heaphopper found that the shortest order is the RHS of the set `{set}: <this sequence>`.
